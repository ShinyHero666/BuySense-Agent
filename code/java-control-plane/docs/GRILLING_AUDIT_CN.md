# BuySense Grilling 反向审查

审查日期：2026-08-14

用户已经明确业务目标、时间边界、项目归属和“工作流与 Agent 按业务选择”的原则。本轮按 Grilling 的设计树对已经确定的方案做反向质询，并用代码和测试回答，不再把可查事实反问给用户。

## 审查中发现并修复

1. 将“上游源码保留”与“Java 主链路已经吸收”分开核对，补上 Java 到 Python/Shopify 数据面的真实桥接。
2. 将远端数据 fallback 默认值改为 false，确认阶段拒绝用本地快照冒充实时价格。
3. 增加确认前价格、库存和兼容性重验，并把刷新后的金额写入购物车草案。
4. 将 Run 并发与速率准入从进程内先计数后插入改为数据库锁事务。
5. 增加有界线程池、全局队列上限、租约 token、续期、过期恢复与旧 Worker 写隔离。
6. 将“一提案一个永久唯一确认 Run”改为“一提案一个有效确认占位”，失败或取消后允许重试，成功后保持唯一。
7. 修复并发幂等竞态中确认请求可能误复用不同请求 Winner 的问题。
8. 增加 Provider 新报价测试、fallback 确认失败测试、租约接管测试、续租测试、原子准入测试和确认失败重试测试。
9. 增加 Python Bridge 鉴权与目录、评论、报价三接口端到端契约测试。
10. 前端依赖更新后 npm audit 为 0 个已知漏洞。

## 剩余风险

- 未配置真实 Shopify 凭证，Bridge 验证的是契约与本地模拟 Provider，不是线上商城验收。
- 未运行真实模型基准，不声明真实模型 Token、延迟或准确率。
- 目录与标签仍是参考和合成数据，不外推为线上 CTR、CVR 或 GMV。
- 支付被明确禁用，只生成购物车草案。
- Java 数据库原子准入会串行化 Run 创建事务；当前吞吐规模下换取正确性合理，若达到高 QPS 应改为独立 admission counter 或分片配额。

最终判断：项目已经形成一条明确主链路，具备真实业务背景、确定性与模型边界、可插拔数据面、运行治理和分层评测。它不再是固定节点串联的玩具工作流，但面试时仍必须如实说明真实 Provider 与真实 LLM 尚未凭证验收。
